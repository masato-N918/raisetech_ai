# レビュー観点チェックリスト

SKILL.md の手順 3（コードレビュー）で使う、観点ごとの確認項目。
上から機械的に埋めるためのものではない。読んでいて気になった箇所について「この観点で見落としがないか」を確かめるために使う。
ここに挙げた例は過去のチェックで実際に見つかったパターンなので、同じ形の問題が別の場所にないかも見るとよい。

## 目次
1. バックエンド（Spring Boot / JdbcTemplate）
2. データベース（PostgreSQL / Flyway）
3. フロントエンド（React / TypeScript）
4. API の設計（フロントとバックの境界）
5. テスト・CI・開発環境

---

## 1. バックエンド（Spring Boot / JdbcTemplate）

**トランザクション**
- 「読んでから書く」処理（存在チェック → 採番 → INSERT など）に `@Transactional` があるか
- 一般的な形：Service クラスに `@Transactional(readOnly = true)` を付け、更新系メソッドだけ `@Transactional` で上書きする

**入力検証**
- リクエスト DTO の `@NotNull` / `@NotBlank` / `@Size` / `@Pattern` が、DB の制約（NOT NULL・VARCHAR 長・CHECK）と対応しているか
- `List<UUID>` のような配列の要素自体の検証（`List<@NotNull UUID>`）が必要か
- 前後の空白の扱い（trim）が、登録と更新で揃っているか

**例外とエラーレスポンス**
- `@RestControllerAdvice` で扱っていない例外がないか：
  - `HttpMessageNotReadableException`（JSON の形式不正、日付の形式不正）
  - `MethodArgumentTypeMismatchException`（パス変数の UUID が不正）
  - 想定外の例外（500）
  扱っていないと、Spring の既定の形式でレスポンスが返り、API のエラー形式がバラバラになる
- Spring 6 以降のエラーレスポンスの標準は `ProblemDetail`（RFC 9457）。独自形式でもよいが、形式が統一されていることが大事
- 例外メッセージが状況に合っているか（更新時なのに「登録できませんでした」など）

**SQL**
- 文字列連結で SQL を組み立てていないか（プレースホルダ `?` を使っているか）
- `LIKE` 検索で、キーワード中の `%` と `_` をエスケープしているか（しないとワイルドカードとして効く）
- `toLowerCase()` / `toUpperCase()` に `Locale.ROOT` を指定しているか
- 一覧取得で、絞り込み結果に関係なく関連データを全件取っていないか（件数が少ないうちは問題にならないが、指摘はしておく）

**構成**
- 動作確認用に一時的に作ったクラス（Hello エンドポイント、接続確認の Runner など）が残っていないか。Javadoc に「不要になれば削除」と書いてあるものは特に
- 1 つのパッケージにすべてのクラスが入っていないか（機能別パッケージ `card/`・`checklist/`・`common/` が一般的）
- インデントがタブとスペースで混在していないか、import 済みのクラスを完全修飾名で書いていないか

## 2. データベース（PostgreSQL / Flyway）

- `ORDER BY` の根拠になっている列が、本当に意図した順序を表しているか
  - 例：`gen_random_uuid()` で採番した UUID（ランダムな v4）は追加順にならない。追加順が必要なら `position` 列や `created_at` 列、または `uuidv7()`（PostgreSQL 18 以降）を使う
- 適用済みのマイグレーションファイルを書き換えていないか（Flyway のチェックサムエラーになる。変更は新しいバージョン `V<n>__...sql` で行う）
- 動作確認用のサンプルデータが、本番用のマイグレーションに混ざっていないか（必須の固定データ＝ボード・リストと、サンプルのカードは分けるのが一般的）
- 外部キーにインデックスがあるか、`ON DELETE` の挙動が要件（例：カード削除時にチェック項目も消す）と合っているか
- `created_at` / `updated_at` のような監査用の列があるか（必須ではないが一般的）

## 3. フロントエンド（React / TypeScript）

**状態の組み合わせ**（不具合が最も出やすい）
- 検索中（絞り込み表示中）に、並び順に依存する操作（D&D・並べ替え）ができてしまわないか
- モーダルの上に別のダイアログを重ねたとき、Esc やクリックのイベントが両方に届いていないか（`window` の keydown を複数のコンポーネントが監視していると両方が反応する）
- 処理中に同じ操作を連打できないか、処理中にモーダルを閉じられないか
- エラーを表示した直後に、再取得の処理がエラーを消していないか
- エラー表示のときに、盤面全体が隠れてしまわないか

**非同期処理**
- 複数の API を順番に呼ぶ処理で、途中で失敗したときに中途半端な状態が残らないか（例：カードは作成済みなのにエラー表示 → 再送信で同じカードが重複する）。サーバ側の 1 トランザクションにまとめられないか
- 検索のように連続して呼ばれる処理で、古いレスポンスが新しい結果を上書きしないか（キャンセル用のフラグや `AbortController`）
- 楽観的更新をしていない場合、操作直後に表示が一瞬元に戻るなどのちらつきがないか

**構成・可読性**
- 1 つのファイルが大きくなりすぎていないか（目安として数百行を超えたら `components/` と `hooks/` に分ける）
- 同じエラー処理が何度もコピーされていないか（`fetch` の共通ラッパーにまとめる）
- テンプレート由来で使っていないファイル（`src/assets/` の画像など）が残っていないか

**アクセシビリティ**
- クリックできる要素が `<button>` になっているか（`div` や `article` に `role="button"` を付けるより、本物の要素を使うのが基本）
- モーダルにフォーカストラップがあるか。ネイティブの `<dialog>` 要素を使うと、Esc・フォーカス管理・背面の操作無効が標準でそろう
- `index.html` の `lang` と `<title>` がアプリに合っているか（Vite テンプレートのままだと `lang="en"`、`title="frontend"`）

**TypeScript**
- `as` による型の上書きが、実際のデータと合っているか（API のレスポンスを `as Card` しているが、実際には一部のフィールドが返ってこない、など）
- 省略可能（`?`）にしている理由が「API によって返したり返さなかったりするから」になっていないか（それは API 側の型の不統一のサイン）

## 4. API の設計（フロントとバックの境界）

- 画面で計算した値を、サーバが同じ前提で解釈しているか（画面は絞り込み後の index、サーバは全体の index、のようなずれ）
- 同じリソースなのに、エンドポイントによってレスポンスの形が違わないか（GET はチェック項目つき、POST/PUT はなし、など）
- フロントにサーバのデータ（UUID など）が直書きされていないか。直書きしている場合、ドキュメントにその理由と対応関係が書かれているか
- HTTP メソッドとステータスコードの使い方（作成 201、削除 204、部分更新は PATCH、存在しない 404、入力不正 400）

## 5. テスト・CI・開発環境

- バックエンド：Controller のテスト（`@WebMvcTest` + MockMvc）、Service の単体テスト、Repository の結合テスト（Testcontainers の PostgreSQL）があるか。特に並び順の計算のような、壊れても気付きにくいロジックにテストがあるか
- フロントエンド：テストの仕組み（Vitest + Testing Library）があるか。比較関数や日付の判定のような純粋関数は、最初にテストを書く対象として向いている
- Java のフォーマッタ・静的解析（Spotless / Checkstyle / SpotBugs / Error Prone）があるか
- oxlint の設定が最小限すぎないか（`jsx-a11y` プラグインや `suspicious` カテゴリを有効にしているか）
- CI（GitHub Actions）で、PR ごとに lint・ビルド・テストが自動で走るか。PR ベースで運用しているなら、自動チェックがあるのが一般的
- `.editorconfig` があるか（インデントの混在を防ぐ）
- `.env` がコミットされていないか、`.env.example` が最新か
